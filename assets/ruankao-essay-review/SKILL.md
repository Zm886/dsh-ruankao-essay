# 软考系统分析师论文自评与批改

对成稿做**逐段体检**，输出可直接照改的问题清单；只依据公开的写作规范与阅卷口径，不引用任何课程资料或他人作品。

## 输入

- 一份论文成稿（`.md` / `.doc` 正文）＋对应题目与三个子题目；
- 若用户只给了正文没给题目，先要求补充题目，否则无法判断切题。

## 一、先用脚本做机械检查

机械项不靠肉眼，直接量：

```powershell
& "<skill-directory>/../ruankao-essay-writing/scripts/make-essay-doc.ps1" -MdPath "<成稿>.md" -OutPath "<临时>.doc"
# 输出：段落数 / 含标点字数 / 纯汉字
```

| 机械项 | 合格标准 | 不合格怎么报 |
|---|---|---|
| 段数 | 正好 10 | 报出实际段数，并指出哪几段该合并或拆分 |
| 含标点字数 | 2500~2800 | 给出差额与需要增删的字数 |
| 标题 | 无 | 指出具体行 |
| 「摘要／背景／子题目」字眼 | 无 | 指出具体句 |
| 「第一／首先／一是」式分点 | 无 | 逐处列出并给改写句 |
| 第一人称 | 除首段身份交代外无 | 逐处列出 |
| Markdown 残留 | 无 `**`、无列表符号 | 逐处列出 |
| 建设期出现位置 | 只在首段 | 指出重复出现的段落 |

## 二、再按段落逐个体检

| 段 | 检查什么 |
|---|---|
| 1 摘要 | 是否含项目、时间、金额、周期、功能定位、本人角色、本文内容概括；是否**点题**（出现题目关键词） |
| 2 缘由 | 是否说明「为什么做」；是否有真实痛点而非套话 |
| 3 概况与技术 | 功能模块与系统边界是否清楚；技术栈是否**给理由**而非罗列 |
| 4 子题目 2 回应 | 题目列出的分类**名称是否齐全**、是否显性点题、是否解释「是什么／怎么落地」 |
| 5~7 正文 | 每个论点是否配了**项目内真实业务实例**（场景＋做法＋结果）；是否只谈技术不谈场景 |
| 8 问题与效果 | 问题是否回挂子题目 2 的能力；效果是否有量化数据 |
| 9 收尾 | 是否 2~3 条不足＋对应改进；是否有空话 |
| 10 结论 | 是否收束全文、不引入新论点 |

## 三、五类高频扣分（按严重度排序）

1. **偏题**：子题目 2 的分类缺项、或用词与题目不一致——必须改，属硬扣分。
2. **模板化**：出现标题、「摘要」「背景」等字眼、成段套话——必须改。
3. **只列技术不写方法**：把框架名当理论名词、缺业务场景——必须改（每条至少补一句项目做法）。
4. **无量化效果**：效果段只有形容性表述——建议改（补指标，宁少勿假）。
5. **行文口径**：分点标号、第一人称、字数越界——建议改（机械项，改起来快）。

## 四、输出格式

按下面结构输出，不要泛泛而谈：

```
一、机械检查
   段数 10 ✓ / 含标点 2634 ✓ / 无标题 ✓ / 分点 2 处 ✗ / 第一人称 0 ✓ / ** 残留 0 ✓

二、逐段结论
   第 4 段：子题目 2 的「双向可追溯性」未显性回应 —— 必须改
   第 6 段：缺项目业务实例，只有技术描述 —— 必须改
   第 8 段：效果无量化 —— 建议改

三、改写建议（逐条给出原句 → 修改句）
   原句：……
   改为：……

四、总体判断
   是否可提交：否；优先修掉 2 处「必须改」。
```

## 五、边界

- **不编造项目数据**：用户没给指标时，建议补指标并把数值标注为「示例，请替换为真实数据」。
- **不照抄他人作品**：只按规范给结构与写法建议，不提供他人成稿的段落。
- 机械项与子题目覆盖是硬项，先报；文采类建议放最后，不要淹没硬伤。

## 与其他技能的分工

- `ruankao-essay-bank`：查题目、理论骨架、写作规格 → 动笔前用。
- `ruankao-essay-writing`：10 段式成稿与 Word 交付 → 动笔时用。
- 本技能：对已成稿做体检与改写建议 → 交稿前用。
