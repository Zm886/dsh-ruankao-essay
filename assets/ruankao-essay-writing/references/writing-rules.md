# 软考系统分析师论文改写——改进点记忆（本次会话沉淀）

> 适用范围：为用户改写软考"系统分析师"论文（含《论基于AI的智能化测试平台架构设计与应用》一篇）。本文档记录用户在逐轮反馈中提出的**硬性要求与踩过的坑**，下次改同类论文直接照此执行，不必再问。
> 本章依据系分论文的通用十段式框架与阅卷评分口径整理。

---

## 一、结构与篇幅（用户明确要求，优先级最高）

| 项目 | 要求 | 本次定稿 |
|---|---|---|
| 段落数 | **严格 10 段式**：摘要 → 背景 2 段 → 回应子题目 2 → 正文 3 段 → 问题与效果 → 收尾 | 10 段 |
| 字数口径 | 用户按 **Word 含标点字符数**（"字符数不计空格"）核对，不是纯汉字数 | 含标点约 2779，纯汉字 2494 |
| 目标区间 | 2500~2700，**2700 上下可接受**，允许到约 2900 | 2779 |
| 周期写法 | **建设周期只写在第一段**，正文不再重复 | 全文仅 1 处 |
| 标题 | **不写标题**（题名不进正文），也不写子题目小标题 | 无 |

**教训**：纯汉字数与 Word 含标点数差约 300，汇报字数时必须说明口径，否则用户会认为"字数超了"。

## 二、行文与语气（用户逐条否掉过的写法）

1. **不要"一问一答"式结构** —— 不允许"在用例设计方面，我的重点是……""这一点由 XX 承担"这种自问自答分块；要按工程推进顺序叙事（立项压力 → 架构选型 → 用例语料 → 夜间执行 → 数据与归因 → 上线波折 → 成效 → 不足）。
2. **不要个人角度** —— 去掉"我带着测试骨干……""我最终决定……"，改为"测试团队……""最终改为……"；本次定稿第一人称出现 **0 次**。仅保留身份句"本人作为系统分析师，参与了……"。
3. **不要机械分点标记** —— 禁用"第一/第二……""一是/二是……""首先/其次"。五方面、五问题都要用因果链串成段落。
4. **不要"念提纲"的宣告式过渡** —— 曾写过"针对题目要求的五个方面，平台在架构上分别作了安排……下面结合项目实践，依次说明各自的架构位置与设计思路"，被否；改成把五方面**融进架构描述收尾的一句**。
5. **举例必须符合实际业务场景** —— 泛泛描述要换成项目里的真实业务：信贷放款／支付结算／理财申赎三条主链路；放款金额取额度上下限、还款期数取极值、利率取浮动区间端点；日终批量与月度结息（夜间窗口、依赖前置账务数据、错过窗口影响次日开门营业）；账户／客户／交易三类实体，零余额账户、临界额度、跨期还款、当日冲正；支付回调超时僵持两天→时间轴对齐→账务接口幂等处理缺陷；还款计划期数与计息区间对不上。
6. **数据可以模糊** —— 允许"大幅提高／明显缩短"这类模糊表述；但原稿自带的硬数据（8 小时→2 小时、82%→98%、7×24）保留。

## 三、三个子题目的回应（评分口径）

- **子题目 1**：首段须含项目、时间、金额、周期、功能定位、我的角色；背景第 2 段**写功能与技术且要"概括解释"而非罗列**。本次做法：技术句后面补"为什么这么选"（"考虑到测试任务与研发现场、流水线强耦合，且 AI 模型需要独立演进……"）。
- **子题目 2**：**必须显性点题**，五方面（AI 驱动的测试用例智能生成、智能化测试执行引擎、测试数据智能管理、缺陷智能分析与归因、持续反馈与模型迭代机制）名称要在文中出现，并说明各自在架构中的落点；本次改为融入第 4 段收尾。
- **子题目 3**：问题与解决办法要**回挂到子题目 2 的架构能力**（"问题出在用例生成的语料上""属执行引擎的调度问题""落在数据管理服务上""是缺陷分析服务的短板"），并且效果与不足同段或紧随其后。
- 通篇不出现"摘要""背景""子题目"这些字眼（模板化会扣分）。

## 四、文档生成的技术要点（踩坑记录）

1. **交付格式**：生成 Word 可打开的 HTML 型 `.doc`（`.md` 作源稿）。样式：`@page A4 2.54cm/3.17cm`；`p{font-family:SimSun;font-size:12pt;line-height:1.5;text-indent:24pt;margin:0;text-align:justify}`。
2. **文件名必须与题目完全一致**：`论基于AI的智能化测试平台架构设计与应用.doc`（用户明确要求过）。
3. **PowerShell 传参会吞掉中文标点** —— 直接在 `pwsh -Command` 里写 `“”` 或 `——` 会失效。必须用码点构造：
 `$q1=[char]0x201C; $q2=[char]0x201D; $dash=[char]0x2014`，再用 `[regex]::Replace(..., ($q1+'$1'+$q2))` 与 `$t.Replace($dash, $dash+$dash)`。
4. **写入被占用**：若用户正用 Word/WPS 打开该 doc，`WriteAllText` 会抛"being used by another process"。做法：循环重试 3~5 次（每次间隔 3 秒），或先另存 `_v2.doc`，释放后再合并回原名并删除临时文件。
5. **编辑工具的两类翻车**：
 - `edit` 的 `old_string` 若写成"自己以为的文本"会匹配失败 —— 改前先 `read` 出确切行；
 - 大段替换时容易把相邻段落吞进 `new_string` 造成**整段重复**（本次出现过效果段重复三次、段落合并成一句的情况）。**大改后必须回读文件并检查组数、重复段**：
 `$lines | Group-Object | Where-Object { $_.Count -gt 1 }`。
6. **生成前自检脚本**：段数、含标点字数、汉字数、第一人称次数（`我|咱`）、"建设周期"出现次数、五方面关键词命中数、是否残留#标题/分点标记。

## 五、下次接到同类任务的推荐流程

1. 先读题目要求的子题目（几个方面）→ 列出关键词清单，确保正文逐个命中。
2. 读用户原文 → 提取项目事实与数据（不改动）→ 标记错别字（按用户要求决定是否保留）。
3. 按 10 段式搭骨架：摘要 / 缘由 / 功能技术 / 回应子题目 2 / 正文 3 / 问题与效果 / 收尾。
4. 用业务实例替换泛泛表述（每个论点至少一个金融业务场景）。
5. 通读去"问答感"与"提纲感"，统一为客观叙述。
6. 压字数至目标区间（优先削删修饰性表述，不动论点与实例）。
7. 生成 doc → 自检 → present → 汇报时同时给出两个字数口径。
