# 软考系统分析师论文写作总纲

用本技能代替即兴发挥：先查题库（同目录的 `ruankao-essay-bank` 技能），再按下面的固定规格成稿。

## 触发场景

- 用户给出「论×××」题目＋三个子题目，要求写一篇论文（押题、模拟、考场备用）。
- 用户上传自己的论文 docx，要求改写／润色／提分。
- 用户给出新题目，要求「按软考论文格式」产出成稿。

## 交付规格（硬约束，逐条自检）

| 项目 | 要求 |
|---|---|
| 结构 | **严格 10 段**（段位基准见下方「10 段位基准」，全仓库与门禁脚本统一以此为准） |
| 字数 | 按**含标点**核对，目标 2700~2800（首次成稿可 2500~2700）；不要用纯汉字数汇报 |
| 标题 | **不写标题**，也不写「摘要」「背景」「子题目」这些字眼（模板化会扣分） |
| 分点 | 不用「第一／第二」「首先／其次」「一是／二是」式列举，改用因果链叙事 |
| 人称 | **全文无第一人称**；只有首段可用「本人作为系统分析师，参与了……」交代身份（「我国」「忘我」等固定搭配不计） |
| 时间 | 建设期**只写在首段**，正文不再重复 |
| 引号 | 中文引号「“”」，不要直引号 |
| 实例 | 每个论点至少配一条**项目内真实业务实例**（业务场景＋技术手段＋结果） |
| 收尾 | 2~3 条不足＋对应改进方向，并给量化效果 |
| 交付 | `.doc`（Word 可直接打开）＋ `.md`（源稿），文件名与题目一致 |

### 10 段位基准（全仓库唯一口径）

段与段之间用**空行**分隔，一段可以自然折行；门禁脚本按空行切块计段，所以请勿用空行在段内断句。

| 段 | 段位 | 必含要素 |
|---|---|---|
| 1 | 摘要 | 项目、时间、金额、周期、功能定位、本人角色、本文内容概括、题目关键词 |
| 2 | 缘由 | 为什么做、真实痛点（不是套话） |
| 3 | 概况与技术 | 功能模块与系统边界、技术栈**给理由**而非罗列 |
| 4 | 回应子题目 2 | 题目列出的分类名称齐全、显性点题、说清各自落点 |
| 5~7 | 正文三段 | 每段一个论点 ＋ 项目内真实业务实例（场景＋做法＋结果） |
| 8 | 问题与效果 | 问题回挂子题目 2 的能力；效果给量化数据 |
| 9 | 收尾 | 2~3 条不足 ＋ 对应改进方向 |
| 10 | 结论 | 收束全文，不引入新论点 |

> 段 9（收尾·不足与改进）与段 10（结论）**必须分开写**：段 9 讲还差什么、怎么改，段 10 收束全文。早期版本把「问题与效果」与「收尾」合并成一段会导致只有 9 段、被门禁判 FAIL。

## 流程

1. **查题**：用 `ruankao-essay-bank` 技能列目录，确认题目出处（年份/试题号）与同类题型的成稿、理论骨架、素材；本地参考资料存在时优先使用。
2. **建骨架**：把子题目 2 要求的分类**逐项列出**（名称必须与题目用词一致，一个不漏），作为正文各段的论点。
3. **选项目**：从题库技能的「作者自有项目背景」挑一个背景；同一项目可跨题型复用（换题不换项目），避免每次编新项目。
4. **配实例**：每个分类各写一条项目做法，落到具体业务（如「日终批量与月度结息」「放款金额取额度上下限」「支付回调超时定位幂等缺陷」），不要只谈技术名词。
5. **写成稿**：按 10 段规格写作，读 `references/writing-rules.md` 规避已踩过的坑（问答式、提纲式、个人角度等）。
6. **对子题目 3**：问题与解决办法要**回挂**到子题目 2 的能力（如「问题出在用例生成的语料上」「属执行引擎的调度问题」）。
7. **自检**：运行 `scripts/check-essay.mjs`（跨平台，Windows 上也可用 `scripts/check-essay.ps1`）——脚本按评分口径检查四类内容：A 格式（段数 10、含标点 2500~2800、无第一人称/禁写字眼/粗体/标题；源稿里的直引号只提示不阻断，因为生成 .doc 时会自动转成中文引号）；B 段落职能（首段含身份与金额周期、建设期只写在首段、末三段含量化效果与不足改进）；C 实例密度（第 4~8 段至少 3 段含具体数字）；D 术语覆盖（`--require-terms` 给出的分类名称必须全部命中，对应子题目 2 的显性点题）。**未输出 PASS 不得交付**；再逐条核对下面的《通用默写检查表》。本地 `references/` 下若另有参考资料，可一并参照。
8. **生成交付物**：调用 `scripts/make-essay-doc.mjs`（Windows 可用 `scripts/make-essay-doc.ps1`）把 `.md` 转成 Word 可打开的 `.doc`（脚本已处理中文标点与编码的坑）。

## 子题目回应规则（决定成败）

- **子题目 1**：首段要含项目、时间、金额、周期、功能定位、我的角色；缘由段写「为什么要做」；概况段写「功能模块＋技术栈」并**解释技术选择的理由**，不要罗列技术清单。
- **子题目 2**：**必须显性点题**——题目列出的分类名称要在正文出现，并说明各自在方案中的落点；这是最容易丢分的地方。
- **子题目 3**：问题→措施→效果，且与子题目 2 的论点一一对应；效果给量化数据。

## 通用默写检查表（每篇写完自检）

- 段数正好 10（按空行切块计段，段内折行不算新段），段位对照上面的《10 段位基准》；建设期只出现在首段
- 含标点字数落在 2500~2800（脚本输出的口径为准）
- 无标题、无「摘要／背景／子题目」字眼；无「第一／首先／一是」式分点
- 全文无第一人称（首段身份交代除外；「我国」「忘我」等固定搭配不计）
- 子题目 2 列出的分类一个不漏，正文逐项回挂
- 每个论点至少一条项目真实业务实例
- 效果段有量化数据；段 9 有 2~3 条不足与改进，段 10 单独收束全文
- 无 Markdown 粗体标记 `**`；正文尽量直接用中文引号「“”」（源稿里的直引号在生成 .doc 时会自动转换，不阻断交付）

## 生成 Word 文档

**优先用 Node 版（macOS / Linux / Windows 通用）：**

```bash
node "<skill-directory>/scripts/make-essay-doc.mjs" --md "<成稿.md>" --out "<成稿.doc>"
```

**Windows 上也可以用 PowerShell 版**（用调用运算符直接执行，**不要**套一层 `pwsh -File`）：

```powershell
& "<skill-directory>/scripts/make-essay-doc.ps1" -MdPath "D:\path\essay.md" -OutPath "D:\path\论题目.doc"
```

脚本要点（若需手写，务必照做）：

- 版式：A4、页边距 2.54/3.17cm、宋体小四（12pt）、首行缩进 2 字符、行距 1.5、两端对齐；
- **按空行切段**：每个空行分隔的块渲染成一个段落，块内折行会合并进同一段；
- **PowerShell 命令行会把中文引号「“”」和破折号「——」弄丢，必须用 `[char]0x201C`、`[char]0x201D`、`[char]0x2014` 构造**（Node 版用同样的码点构造）；
- PowerShell 版脚本本身必须以**带 BOM 的 UTF-8** 保存：Windows PowerShell 5.1 无 BOM 会按 ANSI 误读，中文字符串被破坏后脚本直接报错；
- 输出用带 BOM 的 UTF-8；文件被 Word 占用时 PowerShell 版会重试，仍失败则另存 `*_v2.doc`；
- 脚本会打印「段落数 / 含标点字数 / 纯汉字」，**段数必须为 10**，字数落在 2500~2800。

字数口径提醒：脚本统计时**会剥掉 Markdown 的 `**` 粗体标记**，所以 md 里不要用 `**`（既影响计数又属于考场不认的格式），写完先自查 `**`、`一是/首先` 这类分点残留。

## 边界

- 只做「软考系分论文」这一件事；不做范本抄袭——项目背景与数据由用户确认，未提供时用用户自己的项目并明确标注假设。
- 用户给了自己的原文时，**保留其项目事实与数据**，只改结构、语气、字数与错别字取向（按用户要求决定是否保留原文用字）。
